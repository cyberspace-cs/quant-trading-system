## 一、1 分钟满分口述（直接背）

> 对标九坤的中高频量化系统，整体采用**五层事件驱动架构**，分为数据中台、策略引擎、风控引擎、交易执行、资产台账五层。
>
> **数据层**通过 Kafka + Flink 实时清洗行情与另类数据，构建工业化因子库，Redis 缓存实时因子和盘口数据保障微秒级延迟，海量时序行情用 ClickHouse 存储。
>
> **策略层**结合多因子与 AI 模型实时选股打分、生成调仓信号，支持策略热更新与信号降噪。
>
> **风控**采用九坤典型的矩阵式三层风控，事前规则拦截、事中实时暴露监控、事后回撤熔断，保证交易合规可控。
>
> **执行层**通过 TWAP、VWAP 智能拆单降低冲击成本与滑点，维护完整订单状态机。
>
> 最后 **MySQL 落地所有账务流水**，盘后全量对账归因，实现回测、仿真、实盘全流程闭环迭代。

## 三、高端追问标准答案

### Q1. 如何解决策略过拟合？
- **样本切割**：时间序列严格按时间切训练/验证/测试，禁止随机打乱泄露未来。
- **滚动训练**：walk-forward 滚动窗口重训，适配市场 regime 变化。
- **正则与约束**：L1/L2、Dropout、Early Stopping 限制模型复杂度。
- **样本外验证**：保留 never-touched 样本外集；多周期、多标的、牛熊市分别验证。
- **因子正交**：IC/IR 稳定性优先于单期收益，剔除高相关冗余因子。

### Q2. 滑点如何建模？
分三源动态建模：
- **波动成分**：`slippage ∝ σ × √dt`，高波动时段放大。
- **盘口深度**：`slippage ≈ 委托量 / 盘口挂单量 × tick`，大单吃单成本。
- **拆单频率**：拆得越细、间隔越长，冲击越小但时间风险越大，用 **Almgren-Chriss** 最优执行框架权衡。
- 回测用成交驱动（fill simulation），仿真用真实盘口回放校准。

### Q3. 多策略相关性如何控制？
- **因子正交**：对收益做施密特正交 / PCA，去除共线因子。
- **风格对冲**：行业、市值、风格因子中性化，控制净暴露。
- **仓位互斥**：高相关策略（ρ>0.7）做仓位上限互斥，避免同向加杠杆。
- **风险预算**：按策略波动贡献分配风险预算（risk parity）。

### Q4. 极端行情熔断机制？
- **波动率阈值**：个股/指数 N 秒涨跌超阈值 → 冻结该标的（limit bitmap 置位）。
- **批量冻结**：相关行业/板块联动冻结，防止踩踏。
- **策略级熔断**：单策略回撤超阈值 → `switch=halt` 自动关停。
- **全局熔断**：账户回撤超硬阈值 → 全市场停止新单，仅允许减仓。
- 盘后人工复盘，解冻条件写入配置中心。

### Q5. 低延迟 vs 一致性如何权衡？
- **盘中**：低延迟优先。Redis 做实时展示与决策，允许毫秒级不一致（行情快照、预估盈亏）。
- **盘后**：一致性兜底。以券商柜台回执为唯一真值，MySQL 落地，`ledger.reconcile` 三账合一校准。
- 关键路径（下单）走内存状态机 + 同步柜台回执，非关键（展示/归因）最终一致。

### Q6. Redis 挂了怎么办？
- 行情/因子关键读加**本地缓存兜底**；订单状态机在**内存**维护，不依赖 Redis 持久。
- Redis 丢失可由 **Kafka 重放 + MySQL 校准** 恢复热数据。
- Cluster 多分片 + 主从，单分片故障自动切换，交易核心 Key 独立实例。

### Q7. 订单状态机如何保证不丢单、不重单？
- **order_id 全局唯一**（雪花/UUID），柜台回执按 order_id 幂等落库。
- 状态变更走**版本号/状态机校验**，非法跃迁拒绝。
- 网络抖动：**指数退避重试 + 重试前先查单**（query order）避免重复报单。
- 缺量补单：收盘前对未成部分按策略决策补单或撤单。
